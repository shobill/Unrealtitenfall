# DeathMatch Communication 운영 규칙

이 폴더는 DeathMatch 프로젝트를 확인한 결과를 사용자에게 전달하는 **보고서 보관소**다.

구현 작업 지시서는 이 폴더에 만들지 않는다. 작업이 필요하면 대화에서 사용자가 검수할 수 있는 복사형 프롬프트를 작성하고, 사용자가 직접 원하는 Codex 작업에 전달한다.

## 기본 원칙

1. 이 폴더에는 점검·진단·구현 결과 보고서만 작성한다.
2. 작업 지시, 승인 상태, 진행 관리 문서는 작성하지 않는다.
3. 보고서는 추측과 확인된 사실을 명확히 구분한다.
4. 코드, BP 또는 에셋을 직접 확인하지 못한 내용은 `미확인` 또는 `PIE 확인 필요`로 표시한다.
5. 구현을 수행한 보고서는 실제 변경 파일과 검증 결과를 적는다.
6. 긴 코드 전문이나 원본 로그 전체를 복사하지 않고 판단에 필요한 근거만 기록한다.
7. 보고서를 바탕으로 작업이 필요하면 채팅에서 별도의 작업 프롬프트를 제공한다.

## 폴더 구조

```text
Communication/
├─ 00_README.md
├─ Reports/
│  └─ YYYY-MM-DD/
│     ├─ HHMM_주제_REPORT.md
│     └─ HHMM_다른주제_REPORT.md
└─ Archive/
   └─ Legacy-YYYY-MM-DD/
```

- 보고서를 작성하는 날짜의 폴더가 없으면 `Reports/YYYY-MM-DD/`를 만든다.
- 날짜는 한국 표준시 기준을 사용한다.
- 같은 날짜에 여러 보고서가 생길 수 있으므로 파일명 앞에 24시간제 `HHMM`을 붙인다.
- 정확한 작성 시각을 알 수 없거나 기존 기록을 옮길 때는 `0000`을 사용한다.
- 파일명 주제는 짧은 영문 대문자와 밑줄로 작성한다.

예시:

```text
Reports/2026-09-11/1430_FIRE_SYSTEM_REPORT.md
Reports/2026-09-11/1615_COVER_FALLBACK_REPORT.md
```

## 보고서 형식

```text
# 보고서 제목

- 작성일: YYYY-MM-DD HH:MM KST
- 범위: 확인한 폴더, 코드, BP 또는 에셋
- 구분: 점검 / 진단 / 구현 결과

## 요청 또는 증상

## 결론

## 확인 근거

## 문제점 및 위험

## BP에서 확인할 사항

## 권장 후속 작업

## 검증 상태
```

필요 없는 항목은 생략할 수 있지만 `결론`과 `검증 상태`는 반드시 남긴다.

## 작업 프롬프트 전달 규칙

- 보고서 안에는 실행용 지시서를 누적하지 않는다.
- 사용자가 구현을 원하면 보고서 내용을 바탕으로 채팅에 독립 실행 가능한 프롬프트를 작성한다.
- 프롬프트에는 작업 범위, 요구 사항, 제외 사항, 완료 조건과 검증 방법을 포함한다.
- 사용자가 프롬프트를 검수한 뒤 직접 무거운 모델의 Codex 작업에 전달한다.
- 프롬프트 실행 결과를 다시 확인해 달라는 요청이 오면 새 날짜별 보고서로 기록한다.

## 기존 문서 처리

이 규칙으로 전환하기 전에 사용하던 지시·결과 통합 문서는 삭제하지 않고 `Archive/Legacy-YYYY-MM-DD/`에 보관한다. 이 문서들은 과거 기록이며 새로운 작업 지시로 해석하지 않는다.
